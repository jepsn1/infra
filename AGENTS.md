# AGENTS.md — VPS Operating Manual

Canonical operating manual for this server. Read this before making any infrastructure change.

## System overview

Single VPS hosting development + production for a solo developer. Everything except `/srv/data` is reproducible from Git. Native tooling for development, Docker for production.

- OS: Ubuntu LTS. Dev user: `marcus` (non-root, in `docker` group).
- This repo: `github.com/jepsn1/infra`, checked out at `/srv/infra`.
- Bootstrap: `sudo ./setup.sh` (idempotent, safe to re-run).

## Directory layout

```
/srv
  /infra        this repo — setup, compose, caddy, scripts, backups, docs
  /apps         one directory per application, each its own Git repo
  /data         ONLY persistent state on the machine (never in Git)
    /postgres   postgres cluster data (owned by container)
    /redis      redis AOF data (owned by container)
    /caddy      certificates + caddy state
    /uploads    app file uploads
    /backups    timestamped dumps (see Backups)
  /logs         cron/job logs (e.g. backup.log)
```

Rule: persistent state goes in `/srv/data` and nowhere else. Everything else must be recreatable by `git clone` + `setup.sh`.

## Shared services

Defined once in `compose/docker-compose.yml` (project `infra`):

| Service | Container | Host access (dev) | In-network address (prod) |
|---|---|---|---|
| Caddy | `infra-caddy` | ports 80/443 public | — |
| Postgres 17 | `infra-postgres` | `127.0.0.1:5432` | `infra-postgres:5432` |
| Redis 8 | `infra-redis` | `127.0.0.1:6379` | `infra-redis:6379` |

Manage: `docker compose -f /srv/infra/compose/docker-compose.yml <up -d|ps|logs|restart>`

## Shared Docker network

External network `web` (created by setup.sh). Every production app container and Caddy join it. Caddy proxies to containers **by container name** — apps publish no host ports.

## Reverse proxy

Caddy in Docker, automatic HTTPS. Config: `caddy/Caddyfile` imports `caddy/sites/*.caddy` — one file per app. Add apps with `scripts/new-app.sh <name> <domain> <port> [git-url]`; reload config with `scripts/caddy-reload.sh`. Site files are committed to this repo.

Static SPAs: caddy mounts `/srv/apps` read-only, so a site file can `file_server` an app's build dir directly and proxy only `/api/*` to the app container (see `sites/biblestdy.caddy`).

## Port allocation

- 22, 80, 443: only public ports (UFW). Caddy owns 80/443.
- Production apps: no published ports; internal on `web` network.
- Dev servers: 3000–3999 on localhost, native (not through firewall).
- Shared services bind 127.0.0.1 only (5432, 6379). NOTE: Docker published ports bypass UFW — never publish `0.0.0.0` ports in app compose files.

Host-level `tailscaled` (installed 2026-07-14, via official install script + auth key). This machine: `100.114.149.55`, MagicDNS name `bare-metal`, account marcusklausen@.

- Private (non-public) apps publish container ports bound to the tailscale IP instead of a caddy site — e.g. pkos: `"${TAILSCALE_IP}:3002:3002"` from the app's `.env`. Never 0.0.0.0 (published ports bypass UFW).

## Deployment workflow

Dev is native (VS Code Remote SSH + Claude Code in `/srv/apps/<app>`). Production per app:

```bash
cd /srv/apps/<app>
git pull
docker compose up -d --build
```

Details: `docs/deployment.md`.

## Secrets / environment

- Secrets exist only on the VPS, never in Git.
- Shared-services secrets: `/srv/infra/compose/.env` (generated by setup.sh, chmod 600).
- App secrets: `/srv/apps/<app>/.env`.
- Every repo commits a `.env.example` documenting required vars.

## Backups

Daily 03:00 via `/etc/cron.d/infra-backup` → `backups/backup.sh` → `/srv/data/backups`, log in `/srv/logs/backup.log`.
- `postgres-<stamp>.sql.gz` — `pg_dumpall` of the whole cluster
- `uploads-<stamp>.tar.gz` — `/srv/data/uploads`
- Rotation: 14 days. Restore: `backups/restore.sh` (see `docs/recovery.md`).
- Mirror: every run rsyncs to `/mnt/backup/srv-backups` (second physical drive, set up once via `scripts/setup-backup-drive.sh`). Survives primary-drive failure.
- NOTE: no off-site copy yet (fire/theft) — open TODO.

## Disaster recovery

Full procedure in `docs/recovery.md`. Short version: new VPS → clone this repo → `sudo ./setup.sh` → clone app repos → `backups/restore.sh` → deploy apps.

## Security model

- SSH keys only (password auth disabled by setup.sh once authorized_keys exists), root login key-only.
- UFW: deny inbound except 22/80/443. Fail2ban on sshd. Unattended security upgrades.
- Non-root dev user; containers run unprivileged where images allow.

## Conventions

- Repos: one app = one GitHub repo under `jepsn1/`, cloned to `/srv/apps/<name>` (dir name = repo name = container name).
- Repository contract (each app repo, where applicable): `Dockerfile`, `docker-compose.yml`, `.env.example`, `README.md`, `AGENTS.md`, `Makefile`.
- Docker: compose project/container names = app name; join external `web` network; no published ports; `restart: unless-stopped`.
- App databases: one Postgres database per app on the shared cluster, named after the app.

## Rules for agents

1. Read this file before infra changes; read the app's `AGENTS.md` before app changes.
2. Docs are production code: update README/AGENTS.md/docs/ in the same change as the implementation.
3. Before an infra change, check impact on: caddy config, compose, shared network, backups, setup.sh, recovery docs, app repos. Update all affected pieces together.
4. Significant architecture decisions get an ADR in `docs/adr/`.
5. Keep setup.sh idempotent — new machine state must be installable by re-running it.
6. Prefer automation and single sources of truth over repeated manual edits.
